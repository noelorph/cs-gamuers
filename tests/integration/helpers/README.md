# Isolated account fixtures

`accounts.test.ts` uses real hosted Auth tokens and the ordinary publishable client. It refuses missing credentials, matching demo/test targets, and any target other than the explicitly authorized isolated project. `.env.local` is loaded without printing values. `npm test -- tests/unit` remains usable without integration credentials; `npm test` intentionally requires a prepared integration target.

Apply all `supabase/migrations/*.sql` in filename order. Then, through the approved Supabase connector, verify the selected project ID is `ggiccvcrkydcimveyrfi`, run the URL/ref isolation guard, and install `account-fixture-harness.sql` with `apply_migration`. The SQL marker is operator configuration; it does not independently discover the connected project's identity. Never install this harness on the demo project or include it in application migrations. A repeated installation requires retaining the protected marker and table, and replacing only the function after reviewing its diff.

The harness is executable only by `service_role`, requires the protected test marker and exact caller marker, and owns fixtures through one random run UUID. It exposes a fixed set of reservation/state/session/operation actions, with no arbitrary SQL or global reset. Wrong caller roles, wrong markers, and cross-run account IDs are checked by the integration suite. Native `createUser({email_confirm:true})` is exclusively synthetic test setup, not evidence of participant email ownership. `generateLink` produces fixture proofs without sending mail. Never reuse this confirmation shortcut for demo accounts.

Each normal run removes its own operations, reservation records and canonical accounts, then calls the supported Auth delete API for the exact returned/recorded IDs. If a run is interrupted, inspect only that recorded run's rows in `private.test_fixture_reservations`, call `test_account_fixture('cleanup', recorded_run_id, ...)`, and delete the exact returned Auth IDs. Retain returned IDs until every Auth deletion succeeds; never substitute a project-wide deletion. No database reset is used.

After the final run, verify zero owned fixtures. To uninstall, first verify `private.test_fixture_reservations` is empty, then drop only `public.test_account_fixture(text,uuid,jsonb)` and `private.test_fixture_reservations` through a reviewed test-only DDL migration. Retain the protected `private.environment` marker unless an operator explicitly changes the environment designation.

Generate application types from the final public schema, excluding the test-only `test_account_fixture` declaration. The committed application `Database` type must never advertise fixture administration. This harness is not an implementation of the Task 3 proof, invitation, approval, or maintenance workflows.
